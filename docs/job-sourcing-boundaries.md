# 岗位寻访配置归属与迁移

## 预期与约束

同一个网站场景模板可应用多个任务，一个任务同时寻访多个岗位，按权重分配每日首聊额度。每次执行必须使用当前岗位的 JD、确认事实、FAQ、首聊、职业关键词和推荐条件。通用规则复用不代表岗位业务配置相同。不能串岗位、越权发送或绕过回执核验；测试不访问真实候选人。

## 已验证的根因

1. `task_policy.overlay` 曾将任务首聊、关键词、推荐条件覆盖到每个岗位，导致岗位配置失去优先权。
2. 发布包的岗位 sources 原先只有 JD、事实和 FAQ，缺少岗位寻访参数，因此版本发布无法完整表达岗位差异。
3. `scenario_workspace.compose` 曾将模板首聊写成任务首聊，扩大到所有绑定岗位。
4. 页面把这些字段放在任务执行设置，强化了错误的数据归属；默认关键词还带有招聘行业含义，不适用于其他岗位。

## 修复后的结构

- 场景模板：目标、沟通原则、决策边界、工具规则；首聊模板只作参考。
- 任务：岗位集合、执行窗口、额度、追聊、通知和通用运行限制。
- 岗位：JD、事实、FAQ，以及 job_sourcing（greeting、outreach_terms、recommend_filters）。

岗位配置与 JD 一起进入验证发布包，并进入当前岗位的执行上下文。任务覆盖逻辑只应用通用运行参数，保留岗位专属配置。首聊支持 {{岗位名称}}；推荐条件限制在现有 BOSS 执行器支持的条件范围。空关键词不增加职业关键词预筛，不代表放弃 JD 与业务判断。

入口：任务 → 岗位与事实 → 选择岗位 → 编辑岗位资料与寻访配置 → 保存并验证 → 应用到本任务。任务执行设置只维护任务共用规则。

## 兼容和可验证性

旧发布版本不原地改写。创建新草案时把当前有效业务值转换为岗位 sourcing，校验并发布后持久化。历史任务字段仅保留为兼容数据，不能覆盖显式岗位配置。新任务不再从第一个岗位复制业务参数，默认职业关键词为空。

双岗位测试覆盖不同 JD、首聊、关键词和条件，验证任务参数调整、单岗位发布、模板应用、旧版本迁移和执行上下文均不串用。UI 使用拦截全部 API 写入的浏览器测试。完整后端回归 523 项通过。

平台侧首聊保存仍须按岗位读取与核验。无法核实的岗位仅暂停新增开聊，已有会话继续；本次配置归属修复不宣称已解决平台编辑控件识别问题。

## 规划端与执行端 Agent 的配套修正

任务规划上下文原先仍写“仅岗位事实分别检索”，已改为完整的岗位配置隔离约束。通用计划使用岗位参数占位符，任务级 execution 上下文不再携带职业关键词；岗位寻访配置原文不因本次修改而自动发送模型。规划签名纳入 job_sourcing，防止业务配置变更后复用旧规划签名。

任务级 Agent 结构化补丁不再允许 config_patch.greeting；execution 中出现 outreach_terms 由程序拒绝。岗位补丁只能通过绑定 case_id 的 source_patches.sourcing 提交，支持部分字段更新，由程序合并并校验完整配置，保留本岗位其他字段与其他岗位数据。修改仍只落草案，须测试与发布后生效。模型只看到岗位配置的归属和配置数量，不额外披露原始首聊及关键词。

场景 Agent 保持不读取真实岗位的边界；执行端测试的合成岗位现在显式拥有 sourcing，与生产采用相同的 case_for/overlay 路径，不再借用任务首聊。全局沟通策略与持续决策系统提示明确：通用计划不是事实来源，职业筛选条件不是可对外承诺的事实，不能跨岗位引用。

## 多岗位任务：额度归属与增量变更（2026-11-24）

- **成员表**：任务配置 `members` 记每个岗位的权重（1–10）和首聊状态（参与首聊／已撤下）；`case_ids` 决定成员，二者不一致时以 `case_ids` 为准（`job_members.normalize`）。已撤下的岗位不再首聊，已有会话照常回复、追聊、收简历。
- **额度**：任务每天的首聊目标 = 任务总额（11-25 管理员要求每天用完额度，取消原来按 75%～100% 打折），用最大余数法按权重分给参与首聊的岗位（`job_quota`）。按占位计数，`delivery_unknown` 也算；当天撤下或移除的岗位已用的额度照样计入；账号每天合计不超过 20，多个任务共享这一上限、不在任务间再分配。某岗位当天推荐页没人可联系时，把剩余份额让给其他岗位；只是暂缓的岗位保留份额。
- **验收按岗位复用**：已发布版本的验收结果按岗位记指纹（执行文件签名、任务级设置、该岗位资料，不含 FAQ）。指纹没变的岗位沿用原验收；单个岗位失效只停这个岗位的首聊，全部失效时生成任务级待办。复用的验收与发布门槛同样严格（`incomplete_validation`）。
- **增量变更**：加入岗位只隔离验收新岗位，通过后在执行器安全点写入新版本并换绑 `account_task.release_id`（`job_changes.apply`，与 `faq_answers.apply` 同一模式，原子写入）；期间若有更新的版本（FAQ 换绑或整单发布），这次加入判为失败、不覆盖。权重、撤下、恢复、移除、任务总额同样排队到安全点生效。任务级设置不能借岗位变更修改。
- **不做**：不按岗位拆分追聊底线；不在任务间分配账号额度；不允许账号内重名岗位。
