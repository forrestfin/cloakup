# 一个寻访任务多岗位：共享额度、增量加减、从 BOSS 职位列表选岗位

日期：2026-11-24　状态：设计待确认

## 意图

管理员希望一个 BOSS 寻访任务同时寻访多个岗位，所有岗位共用任务的每日首聊额度，按权重分配；岗位可以随时加入或撤下，不必整单重新发布、暂停任务；新岗位直接从 BOSS「职位管理」里已发布的职位勾选，而不是逐个粘贴编辑页链接。

## 现状（2026-11-24 代码核对）

- 任务 `config.case_ids` 已支持 1–20 个岗位（`platform.py:81-82`），执行器按顺序遍历（`autopilot.py:829-958`），某个岗位首聊成功一批后本轮即结束（`autopilot.py:958`），额度容易被排在前面的岗位用完。
- 额度：`daily_attempts(store,'first_contact')` 统计**整个账号**当天首聊（`autopilot.py:240-251`），却与**每个岗位**各自的随机目标 `daily_new_target(case)`（配置值 75–100%，`autopilot.py:588-593`）比较。`daily_new_limit` 范围 0–20（`job_config.py:15,22`），由 `task_policy.overlay` 抄到每个岗位。
- 岗位来源：只能粘贴 `job/edit?encryptId=…`（`boss.validate_job_url`），`read_job` 读 JD；没有读取职位列表的代码。
- 推荐牛人页：`boss_recommend.open_list` 只核对当前显示的岗位（frame URL `jobid==encryptId` 且标题可见），**不会切换岗位**；当前显示的不是本岗位就报错停下。所以现状下多岗位任务实际只有页面上恰好选中的那个岗位能首聊。
- 收件归属：新会话按 `case['job']['label'] in row['text']` 认领（`autopilot.py:521-524`），同名岗位被拒绝绑定（`workbench.py:698-700`）。
- 发布：发布包含 `config(case_ids…)`、每个岗位一份 `sources`、`plan`、`conversation_prompt`；验收场景按岗位生成（`default_fixtures`，每岗位 8–9 个，互不依赖）；`signature(bundle)` 覆盖整包 + 28 个执行文件哈希 + 模型/策略；加减岗位 = 新草案 → 全量验收 → 暂停 → 发布 → 恢复。唯一的运行中换绑例外是 `faq_answers.apply`：派生版本带 `tested_version_id`，`assert_release_ready` 要求除 FAQ 外与已验收版本一致。

## 目标

1. 任务设一个每日首聊总额，岗位按权重分配，用不掉的额度让给其他岗位。
2. 从 BOSS 职位管理列表勾选「开放中」职位加入任务。
3. 加入岗位：只验收这个岗位的场景，通过后在执行器安全点并入正在运行的任务，不暂停、不重验其他岗位。
4. 撤下岗位、调整权重：不需要验收，在安全点生效。
5. 执行器能在推荐牛人页切换到要首聊的岗位。

## 非目标

- 不提高账号每日首聊上限（仍为 20），不改追聊底线、执行时段。
- 不自动跟随 BOSS 上职位的增删（不自动加入新发布的职位、不因 BOSS 关闭职位自动撤下）。
- 不改变答复、追聊、收简历的逻辑。
- 不改 BOSS 平台上的职位内容。

## 反目标（技术上能跑也算失败）

- 撤下岗位后，已经在聊的候选人没人跟进（回复、追聊、收简历中断）。
- 新岗位没经过它自己的验收就发出首聊；或者代码、模型、策略变了，旧验收结果仍被复用。
- 加岗位让当天账号首聊总数超过 20，或撤下再加回来让当天额度重置。
- 串岗位：首聊在 A 岗位的推荐页用了 B 岗位的问候语/筛选条件，或会话被归到错误岗位。
- 岗位名称、行业词写进代码或提示词（约束 8）。

## 做法对比（管理员已选 1）

1. **增量发布（已选）**：每次加/撤/改权重都生成一个新发布版本；没变的岗位沿用原验收结果，只验收新增岗位；在安全点换绑，沿用 `faq_answers.apply` 的机制。保留"一个任务一个生效版本"，约束 6 的例外从"FAQ 答案"扩到"岗位加减与权重"。代价：要把验收结果从"整包签名"改成可按岗位复用。
2. 岗位成员表放到发布包外：加减更轻，但版本不再完整描述任务行为，恢复和审计要重做。
3. 一个岗位一个任务、共用账号额度池：与"一个任务多个岗位"不符，已排除。

## 设计

### 1. 验收结果按岗位复用

把现在的整包签名拆成三部分：

- `runtime_signature`：执行文件哈希、语义/SDK/套件版本、模型、网关、沟通策略（即现 `signature` 中除 `bundle` 外的全部）。
- `task_digest`：发布包里与岗位无关的部分——`conversation_prompt`、`plan`、`config` 中除 `case_ids`、岗位权重、撤下状态以外的字段。
- `source_digest`：每个岗位那份 `sources` 条目（现有）。

`task_digest` 不含任务每日总额 `daily_new_limit` 和岗位权重（改这些不需要重验）；`source_digest` 计算时去掉 FAQ（沿用今天 FAQ 换绑的例外）。〔实现者核对时补充，设计方决定〕

一次验收记录（`agent_test`）记下它覆盖了哪些岗位，以及当时的 `runtime_signature`、`task_digest` 和各岗位的 `source_digest`。一个岗位"已验收"的条件：能找到一条通过的验收，其 `runtime_signature`、`task_digest`、该岗位 `source_digest` 与当前完全一致。**任务里的每个岗位都要求已验收，包括已撤下但仍在回复候选人的岗位**——撤下只停新首聊，回复、追聊仍是给候选人发消息。〔设计方决定〕

判定按岗位进行：`availability(cid)` 对未验收的岗位返回不可发送，只停这个岗位并生成待办；`runtime_signature` 或 `task_digest` 变化时所有岗位同时失效，表现与今天整单 `release_changed` 一致（`assert_release_ready` 仍在启动时整单检查）。〔设计方决定〕代码或模型变了 → 所有岗位都需重验，与今天一致。

现有的整包验收照旧可用（覆盖全部岗位），FAQ 换绑的 `tested_version_id` 机制合并进这个判定（FAQ 变化不影响已验收状态，沿用今天的例外）。

### 2. 增量变更：加入、撤下、调权重

新增"岗位变更"操作，统一走：生成派生版本 → （仅加入时）验收新岗位 → 排队 → 执行器安全点应用（同一事务写 `agent_bundle`、`agent_release`、`task`、`case`、`account_task.release_id`，与 `faq_answers.apply` 一样）。

- **加入**：从基础版本复制，追加新岗位的 `sources` 条目和成员记录；只用新岗位的 `default_fixtures` 跑一次 validate；通过后可提交应用。验收期间基础版本若变化（比如另一个岗位被撤下），提交时基于新的基础版本重新组装；只要 `task_digest` 和新岗位 `source_digest` 未变，验收结果仍有效。
- **撤下**：成员状态改为"已撤下"。不再发起新的首聊，但这个岗位**仍属于任务**：收件同步、回复、追聊、收简历照常，直到管理员在它没有进行中的会话时彻底移除（彻底移除同样走增量变更，无需验收）。撤下的岗位可以再恢复为参与首聊，无需重验（只要验收仍有效）。
- **调权重 / 改任务总额**：只改成员记录或额度字段，无需验收。任务总额只能在 0–20 范围内。
- 加入时新岗位不能已被其他未停止任务管理（沿用现有检查）；与**账号下所有未停止任务**中已有岗位同名的拒绝加入（收件按名称归属，沿用 `workbench.py:695-700` 的全账号检查）。
- 每次应用写 `logbook.log`（actor、reason）、任务历史，并发事件消息；涉及事件文字时同步 `daily_report.EVENT_RULES`。

任务未运行时，同样的操作直接应用，不必等安全点。现有"整单草案 → 全量验收 → 发布"流程保留，用于改任务级配置、计划、提示词。

### 3. 每日额度按权重分配

- 任务级 `daily_new_limit`（0–20）为管理员配置的总额。当天实际总目标 = 按"日期 + 任务 id"稳定取 75–100%（沿用现有做法，只是种子从岗位换成任务）。
- 每个参与首聊的岗位有权重（整数 1–10，默认 1）。当天份额 = 总目标按权重比例分配（最大余数法取整）。
- 计数：与现有 `daily_attempts` 同口径，按**占位**计（`claimed_at` 当天，含送达结果不明 `delivery_unknown`，以及平台外观察到的首聊），宁可少发不多发。任务当天首聊数 = 当天属于本任务岗位（含当天被撤下、移除的岗位）的占位数；岗位计数同理。撤下再加回、当天新加入都不会重置额度。〔设计方决定〕
- 账号硬上限：账号当天全部首聊（现 `daily_attempts` 全局计数）≥ 20 时，任何任务都不再首聊。同一账号若有多个寻访任务同时运行，它们之间不另做比例分配，各按自己的总额、共同受 20 的硬上限约束（目前同一网站和场景只建一个任务，多任务并行不是常态）。〔设计方决定〕
- 选岗位：每次首聊批次前，从"还有份额、今天推荐页没被标记为没人"的岗位中，选"已用/份额"最低的；权重高者优先打平。若所有还有份额的岗位都没人可聊了，剩余额度按权重让给仍有候选人的岗位，直到任务总目标。
- "今天没人可聊"：推荐页读到 0 张卡，或全部被筛选条件/已联系排除；当天对该岗位不再尝试（份额让出），第二天重置。
- 一个批次仍只做一个岗位；批次结束返回收件检查（现有节奏不变）。删除 `autopilot.py:958` 的"首聊成功就结束本轮"改为由调度决定下一批次。
- 界面在任务上显示：总额、今日目标、各岗位权重/份额/已用。

### 4. 从 BOSS 职位管理读取列表

- 新增只读读取：打开职位管理页，读取每个职位的名称、`encryptId`、城市、状态（开放中/已关闭等）。不点击任何修改按钮。
- 实现前先在真实页面只读观察一次 DOM，再写读取代码和对应的离线 fixture 测试；字段以真实页面为准。
- 界面：任务的岗位区新增"从 BOSS 选择岗位"，列出全部职位，标出已在本任务、已被其他任务管理、已关闭（不可选）；勾选后对每个职位走现有 `boss_bind` 流程（`read_job` 读完整 JD、AI 起草问候语/关键词/条件），岗位进入"待确认"。
- 管理员确认问候语、已确认事实、FAQ、筛选条件后点"验收并加入"，触发第 2 节的加入流程。事实和 FAQ 不能从 BOSS 读取，仍由管理员确认。
- 粘贴链接的旧入口保留。
- **任务运行中谁用浏览器**：执行器运行时独占 BOSS 浏览器（`workbench.create` 在忙时拒绝新操作）。读职位列表和读 JD 做成**执行器在安全点代办的只读步骤**：管理员发起请求 → 排队 → 执行器在下一个安全点、且在任务执行时段内完成读取后回到原循环；任务未运行时走现有入口直接读取。时段外发起的请求等到时段内再读，界面显示"等待执行器读取"。代办步骤只导航和读取，不点击任何修改控件。〔设计方决定〕

### 5. 推荐牛人页切换岗位

- `open_list` 在 `verify_list` 之前，若当前页面岗位不是目标岗位，使用页面上的岗位选择控件切换到目标 `encryptId` 对应的岗位，然后仍由 `verify_list` 核对（核不实只放下这个岗位这一批，不暂停整单，约束 5）。
- 切换控件的结构需先在真实页面只读观察确认；不改变现有随机节奏。
- 每次切换后问候语核验（`greeting_policy`）照旧按岗位进行。

### 6. 收件归属

保持按会话上的职位名称归属（`.source-job`）；账号下所有未停止任务内同名岗位禁止共存。撤下的岗位仍参与认领，所以撤下后新进来的该岗位会话也有人跟进。彻底移除后，该岗位新会话不再被本任务认领（与今天未绑定岗位的行为一致）。

### 7. 待办与提示

由 `attention.reconcile` 生成并自动关闭：
- 新岗位验收未通过（说明失败场景，可重试）。
- 增量变更排队超过一定时间仍未到安全点（例如执行器被页面问题卡住）。
- 某个参与首聊的岗位在推荐页连续切换/核对失败（只停这个岗位的首聊）。
- 已撤下岗位已无进行中会话，可以彻底移除（提示，非必须处理）。

## 约束对照

- 约束 1、2、3：首聊路径不变，切换岗位后仍先核对岗位再发送。
- 约束 4：恢复轮次不应用增量变更。
- 约束 5：单个岗位切换/核对失败只停该岗位首聊。
- 约束 6：增量变更是对现有 FAQ 换绑例外的扩展，仍需新岗位通过隔离验收；需在 CLAUDE.md 约束 6 中写明新例外。
- 约束 7、8：职位列表只在本地读，不进模型；岗位名只作为参数。
- 发布签名：本改动会改动签名文件，上线时需按现有流程重建 → 全量草案验收 → 发布 → 恢复一次。
