# 首聊前按岗位必须项初筛 设计

日期：2026-11-27　状态：管理员已确认（2026-11-27）

管理员已定：方案 A；脱敏经历正文送模型，不另设授权；宁缺毋滥，额度是上限不是目标；必须项改动在安全点生效。标“实现者的判断”的条目待管理员核对。

## 1. 为什么做

拿到的简历匹配度不高。每天首聊额度少（账号上限 20），是稀缺资源。现状（11-26 日报）是开聊 20 次、“审阅后暂不联系 0 位”，开聊前的筛选形同虚设：

- 卡片层只有 BOSS 推荐自带的学历／年限条件和“卡片文字里有没有岗位关键词”（`autopilot.first_contact`）。
- 模型首聊决策（`decision_runtime.initial_contact_decision`）只看到年限、学历、命中的关键词，且提示词要求“有线索就联系，明显无关才等待”。
- 资料弹层的经历全文（`boss_recommend.profile_overview`）已经读到本机，只用来核对收件人，没用来判断匹配。
- 客户反馈的具体要求没有地方沉淀；简历评分（`resume_scoring`）只对照 JD 的已确认要求，结果只进飞书。

客户的“不合适”通常是几条硬性条件，例：QE 工程师岗位 ——“必须有 SQE（供应商质量）经历”“第一学历统招大专”。这两条都要看完整经历才判断得了，卡片看不出来。

## 2. 目标、非目标、反目标

目标
- 每个岗位有一张“必须项”清单，来源是 JD 和客户反馈，管理员可随时增改。
- 首聊前打开资料弹层，按必须项逐条核对；有任何一条明确不符合就不开聊。
- 简历评分用同一张清单；客户反馈改一处，初筛和评分都生效。
- 每个跳过都能说清“哪一条、依据是什么”，管理员可抽查。

非目标
- 不做加权打分排序、不做“相似候选人推荐”。
- 不改 BOSS 推荐页的筛选条件集（仍只用已核实的学历／年限选项）。
- 不改首聊之后的对话、追聊、收简历流程。

反目标（做成这样就算失败）
- 把“写不清楚”的候选人一律当不符合，导致合格的人被大批误杀。标准要“放宽一点”。
- 为了凑额度降低标准。管理员 11-27 决定：宁缺毋滥，额度用不完可以接受。
- 打开资料的节奏变快、变规律。

## 3. 约束

- 约束 7：送模型前用 `redact` 隐去姓名、称呼、联系方式、证件／平台标识、年龄性别；单位、学校、城市保留。管理员 11-27 确认：首聊前把脱敏后的经历正文送模型，不需要像简历评分那样的单独授权记录。CLAUDE.md 约束 7 中“Harness 决策载荷只含意图标签与资料状态”仍成立——初筛是独立的模型调用，不进 Harness 决策载荷。
- 约束 8：必须项是岗位参数，代码、正则、提示词不写任何岗位或行业词。
- 约束 6：必须项属于岗位寻访配置（`job_sourcing`），随岗位进入已签名的发布版本。管理员 11-27 决定：必须项改动和 `faq_answers.apply`、`job_changes.apply` 一样，作为第三个例外，在执行器安全点换绑，不中断任务；生效前须通过本岗位的隔离验收。CLAUDE.md 约束 6 同步写上这一条。
- 约束 5：单个候选人初筛失败（模型超时、脱敏不过）只放下这一位，不暂停任务。
- 节奏：沿用现有 `lognormal` 停留和每批 3–8 位的审阅上限，不加快。
- `job_sourcing.py`、`autopilot.py`、`decision_runtime.py`、`boss_recommend.py` 都在发布签名里，改完要重建 → 草案 → 验收 → 发布 → 恢复。

## 4. 方案比较（管理员已选 A）

| 方案 | 做法 | 取舍 |
|---|---|---|
| **A. 必须项清单 + 模型逐条核对（选中）** | 岗位配置一张必须项清单；首聊前把脱敏经历正文交模型，对每条给“符合／不符合／看不出”和依据；程序按规则决定 | 每次跳过都可解释、可核查；每看一份资料多一次模型调用 |
| B. 纯规则匹配 | 关键词／正则在正文里找 | 无模型成本；“统招”“第一学历”写法多变，判断不可靠；规则只能由管理员逐条配，维护重 |
| C. 反馈原文直接喂模型 | 不结构化，把客户原话附在提示里 | 最快；条件越积越乱，跳过原因说不清，无法核查 |

## 5. 设计

### 5.1 必须项数据

`job_sourcing` 增加键 `must_haves`（`job_sourcing.KEYS` 扩展，`resolve` 对旧数据补 `[]`）：

```
must_haves: [
  {"id": "mh_xxxx",            # 稳定标识，程序生成
   "text": "有 SQE／供应商质量相关工作经历",   # 1–60 字，可直接拿去核对的一句话
   "source": "jd" | "client_feedback",
   "note": "客户 11-27：上一位没做过供应商质量",  # 可选，≤120 字，只给管理员看，不送模型
   "added_at": 1764200000}
]
```

- 每岗位最多 10 条。另存 `must_haves_revision`（清单内容哈希），用于判断旧的初筛结果是否过期。
- 必须项不是对外事实，不进 `facts`/FAQ，不会被回复候选人引用。

### 5.2 录入：管理员把客户反馈说给系统

维护位置：菜单“任务”→ 打开任务 →“岗位与事实”→ 选岗位 →“必须项”区块（管理员 11-27 确认）。菜单“岗位”的岗位详情页对已加入任务的岗位只读，只展示必须项并给“去修改”链接跳到这里。

```
QE 工程师 · 必须项（3 条）                    [+ 录入客户反馈]
────────────────────────────────────────────────────────────
1  有 SQE／供应商质量相关工作经历    客户反馈 11-27   [改] [删]
   客户原话：上一位没做过供应商质量
2  第一学历统招大专及以上            客户反馈 11-27   [改] [删]
3  5 年以上质量岗位经验              JD               [改] [删]
────────────────────────────────────────────────────────────
近 7 天初筛：审阅 64 · 不符 41（第 1 条 30，第 2 条 11）· 开聊 18
```

- 每条显示来源、日期，客户原话（`note`）显示在条目下方。
- 底部统计行：近 7 天本岗位审阅数、不符数（按条目分计）、开聊数，数据来自候选人 `screening` 记录，让管理员看出哪一条挡人过多（可能写得太严或模型理解偏）。

- 主入口：任务 →“岗位与事实”→ 编辑岗位资料与寻访配置。复用现有规划对话（`agent_workspace` 的 `source_patches.sourcing`），在 schema 中允许 `must_haves`。管理员输入客户原话（如“客户说必须做过 SQE，第一学历要统招大专”），模型拆成条目草案，管理员看到逐条列表后确认。
- 同一页面提供直接增删改条目的表单（不经过模型）。
- 两种入口保存后都一样：写成本岗位的待生效变更（参照 `faq_answers.apply`／`job_changes.apply` 的做法，如 `must_haves.apply`），只跑本岗位隔离验收，通过后在 `autopilot` 安全点换绑，任务不暂停；`must_haves_revision` 随之变化，旧的初筛结论自然过期。验收不通过生成待办，说明哪一条没过；待生效期间仍用旧清单。换绑时写 `logbook.log`。
- 隔离验收的 9 个场景中加入一条：必须项非空时，初筛调用的输入不含身份信息、输出结构合法。

### 5.3 首聊前初筛

位置：`autopilot.first_contact`，在 `open_profile` 成功之后、`initial_contact_decision` 之前。

1. 岗位 `must_haves` 为空 → 行为与今天一致，不初筛（今天页提示“本岗位未设必须项”）。
2. 若该候选人已有 `screening` 且 `revision == must_haves_revision` 且结论为不符合 → 根本不打开资料（在卡片循环里就跳过，与现有冷却检查放一起）。
3. 取本次已读到的资料文本（`profile_overview`，弹层“经历概览”之后的全文）加卡片字段（年限、学历、摘要、工作经历），本机 `redact`（现在硬截 1600 字，加一个长度参数，初筛取约 6000 字；截断不拒绝；默认值不变，不影响对话脱敏）。资料全文不落库，只存每条结论和 ≤60 字依据。
4. 模型调用（新模块 `cloakup/screening.py`，与 `resume_scoring` 同样经已授权网关、`effort='low'`），输入：`must_haves` 的 `text` 列表 + 脱敏资料文本；输出 schema：
   ```
   {"items": [{"id": "...", "verdict": "met"|"unmet"|"unclear", "evidence": "≤60字，摘自资料原文或写'资料未提及'"}]}
   ```
   提示词要点：只依据资料；资料没写到的是 `unclear`，不是 `unmet`；只有资料明确写出相反情况才是 `unmet`（例：学历经历里第一段是高中→本科自考，对“第一学历统招大专”判 `unmet`；只写了“本科”未写入学方式判 `unclear`）。
   11-27 只读演练后管理员改严：要求某类工作经历的必须项，资料列出了工作经历但其中没有任何相关职位、职责或项目，判 `unmet`；资料没有列出工作经历时仍 `unclear`；入学方式、证书等常不写的事项仍 `unclear`。简历评分的必须项判定共用同一条（`resume_scoring.EXPERIENCE_RULE`）。
5. 程序判定：任一 `unmet` → 不开聊；否则（全部 `met`／`unclear`）→ 进入现有 `initial_contact_decision`，再按今天的流程开聊。
6. 结果写入候选人 `screening = {revision, at, items, outcome: "pass"|"reject", unclear_ids}`，`store.audit(case,'precontact_screening',...)`，`logbook.log('model', ...)`。
7. 不符合的候选人：`first_contact` 在 `open_profile` 后已经 `add_candidate` 建档，初筛放在建档之后，直接写 `screening`，按 5.3 第 2 步长期跳过；必须项改动（revision 变）后才可能重新初筛。
8. 失败（模型超时、脱敏后为空、输出不合 schema）：这一位冷却 `jitter(1800)` 后可再试，不暂停任务、不算拒绝；连续多次失败生成待办“初筛暂不可用”，恢复后 `attention.reconcile` 自动关闭。
9. 跳过后的关弹层、在列表继续往下看，复用今天“模型选择暂不联系”的分支（停留 `lognormal`、`close_profile`、`read_cards`）。

`initial_contact_decision` 的提示词把“有线索就联系”改为“已通过必须项初筛，按 professional_context 再看一遍”，不再承担主要筛选；载荷里只加 `screening_passed: true` 和 `unclear_count`（数字，不放正文）。

### 5.4 简历评分用同一张清单

`resume_scoring.evaluate` 的输入增加 `must_haves`（text 列表）和首聊前标为 `unclear` 的条目；输出增加 `must_haves` 逐条结论。规则：任一 `unmet` 时 score 不超过 2，评语点名哪一条。飞书消息里列出“待核实：第一学历是否统招”之类，方便顾问在交接前核对。

### 5.5 额度与日报

- 11-25 的“每天必须用完首聊额度”改为：额度是上限，不是目标；筛不出合格的人就不聊。`job_quota.task_target` 的口径不变（仍是上限），去掉相关注释与“额度未用完”类提示（若有）。
- 每批审阅上限保持 3–8；另设每账号每天打开资料的上限（默认 80，配置只能更严），按岗位权重分份额（同 `job_quota.allocate`），到上限后当天不再审阅推荐，避免为了找合格者无限浏览，也避免一个标准严的岗位把别的岗位的浏览份额用光。（实现者的判断，待管理员核对）
- 一批里审阅的人全部被初筛拒掉时，`first_contact` 返回新结果 `'screened_out'`：本岗位按今天 `outreach_exhausted` 的方式让位一段时间（`jitter` 冷却，有上限），轮到其他岗位。
- 其他岗位让出的首聊额度仍按权重再分（`pick_case` 现有逻辑保留）：再分给的岗位同样要过初筛，不降低标准。（实现者的判断，待管理员核对）
- 日报与今天页：按岗位显示“审阅 N、初筛不符 M（按必须项分条计数）、看不出 K、开聊 X”。`daily_report.EVENT_RULES` 与 `tests/test_daily_report.py` 同步。

### 5.6 上线前演练

开聊前的弹层全文没有落库，无法原样重放，用替代样本：用新代码对线上已开聊候选人的 `online_resume.sections`（加卡片字段）只读跑一遍初筛（`.tmp_incident/` 脚本，`/tmp/newpkg`），统计“按新规则会被跳过的人”和他们后来的结果（有无回复、有无简历）。抽约 20 条逐条结论给管理员看，由管理员判断误杀是否可接受，不设硬性门槛。（实现者的判断，管理员未另行指定）

## 6. 测试（TDD，`tests/test_screening.py` 等）

- 必须项为空：不调用模型，流程与今天一致。
- 任一 `unmet` → 不开聊、写 `screening`、关弹层继续；同 revision 下次不再打开资料；revision 变后会重新初筛。
- 全部 `unclear` → 照常进入首聊决策。
- 初筛输入不含姓名、联系方式、年龄性别（用带这些字段的样例资料断言）。
- 模型失败 → 只冷却这一位，任务不暂停；连续失败出待办，恢复后自动关闭。
- 代码与提示词中无岗位词（沿用现有“无硬编码岗位词”的检查方式）。
- `job_sourcing.checked` 对 `must_haves` 的校验（条数、长度、字段）；旧数据 `resolve` 补空列表。
- 评分：有 `unmet` 时 score ≤ 2。
- 每日打开资料上限生效。
