# 历史会话身份核验与有限恢复

## 预期与约束

核验目标是确认“此次打开的会话＝目标会话 ID＋候选人＋当前岗位”，不是观察到浏览器点击就视为成功。核验不通过不得发送消息、索取资料或将内容关联到错误候选人。可以重读页面、有限次重新选中；不能无限重试，也不能强制点击、猜测身份或绕过核验。

## 现场事实

2026-11-18 的执行记录连续出现“岗位读取待下轮核验：历史会话的收件人或岗位尚未核实”，间隔约三分钟，期间有多次选择点击。执行器心跳正常，页面读取通道并未整体断开，但没有形成可解释的失败预算或新的恢复事件。排查前暂停原任务，确保业务执行和诊断互斥。

## 多个根因与证据

1. **布局假设脆弱**：旧 `IDENTITY_JS` 把详情容器第一行直接作为收件人，且扫描所有数字形态的 `[data-id]`。第一行说明文字、姓名旁边附加信息、非会话节点或隐藏重复行均可能破坏匹配。隔离 DOM 测试复现前置说明与隐藏重复行；这是已验证的算法缺陷，不声称已保存原故障瞬间的完整 DOM。
2. **恢复类型漏接**：`inspect_row` 在六次检查失败后抛普通 `SourcingError`；账号调度只对 `ChatSelectionUnavailable` 启用三次恢复预算。因此该错误落入通用“等下轮”分支，无限重试。调用链与现场日志直接支持此结论。
3. **规则不一致**：导入历史会话与已绑定会话读取使用各自的头部匹配逻辑，容易出现一种路径成功、另一种失败。
4. **可观测性不足**：旧错误没有留下姓名／岗位证据缺失环节，运营页只展示笼统“下轮核验”。未绑定候选人时，诊断也可能找不到原失败目标。

## 修复

- 共用 `IDENTITY_READER_JS`：仅接受可见的真实会话行，读取姓名字段，核对详情内精确姓名／岗位字段与唯一会话 ID；不再使用第一行猜姓名。
- 不从消息正文、输入框或整个列表容器取身份；错人、错岗位、错 ID、同名歧义仍拒绝。岗位不再采用子串匹配。
- `inspect_row` 失败抛结构化 `ChatSelectionUnavailable`，接入已有有限恢复。按任务检查间隔退避，最多三次；耗尽暂停并进入管理员恢复待办，沿用任务配置的通知链路。
- 记录无正文的字段匹配计数／缺失阶段及最后失败目标；未导入的历史会话也能按唯一平台会话 ID 进行诊断。
- 环境诊断增加“当前会话身份与岗位”探针，只返回匹配证据，不返回候选人正文。

## 验证与限制

- 504 项全量回归通过。
- 隔离浏览器覆盖前置说明、隐藏重复行、错人、正文中冒用姓名、岗位子串、错 ID、同名歧义，以及共用消息快照读取。
- 真实 CloakBrowser 环境六项检查通过；已有目标会话身份、消息列表、唯一编辑器核验通过，诊断实际发送 0 条消息。证据：`runs/verification/identity-real-target.json`。
- 原业务配置九项实际 Harness 隔离验收通过，保持模板与业务设置不变，证据：`identity-task-validation.json`。
- 自动审批审核拒绝诊断后自动恢复真实任务，认为缺少明确恢复授权。没有绕过该限制。随后用户明确回复“恢复”，继续完成真实失败目标验证和恢复。

## 恢复后捕获的实际故障

首次恢复后捕获原目标 `identity_ambiguous`：25 条可见会话中有两条同名、同岗位显示名匹配。新恢复预算正常记录第 1/3 次并暂缓，没有发送该会话。再次暂停并选中原失败目标后，现场确认平台唯一选中行带 `.geek-item.selected`。因此补充：以平台选中行 ID 消除同名歧义，再核验详情姓名与岗位；选中行与目标 ID 不同、选中行多条时仍拒绝。没有选中证据时，仍须唯一匹配，绝不按同名顺序猜人。

最终真实原失败目标核验通过：唯一选中会话 ID、姓名、岗位、消息列表和唯一编辑器均通过，`incident_resolved=true`，诊断发送 0 条。证据 `identity-original-ambiguous-target.json`。按用户“恢复”授权重新启用任务，已观察到新的 `conversation_bound` 和 `history_synced`，监控样本保存在 `identity-resumed-monitor.json`。最终环境核验通过，但原生输入仍有约 39 秒的耗时警告，属于另一个性能问题，未声称在本次修复。
