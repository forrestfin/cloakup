# 任务飞书通知

每个任务独立保存 `config.notifications`：

```json
{"enabled": false, "resume_chat_id": "", "todo_user_id": ""}
```

`resume_chat_id` 填写目标群的 `oc_...` ID，`todo_user_id` 填写指定管理员的 `ou_...` Open ID。两项独立生效；启用前至少配置一个目标。通知以飞书应用机器人身份发送，机器人需要加入简历群，管理员需在应用可用范围内。

服务端通过 `LARK_APP_ID`、`LARK_APP_SECRET` 环境变量配置自建应用。不要填入任务 JSON，也不要将 Secret 放进前端、提示词、日志或源码。配置应用的机器人能力、发送消息与上传文件权限，并发布生效。Docker Compose 已传递这两个环境变量；日常 `scripts/docker_up.py --reuse-runtime` 保留当前容器已配置的凭据。首次配置或轮换凭据时，通过部署进程环境注入新的 `LARK_APP_ID`、`LARK_APP_SECRET`，再运行 `scripts/docker_up.py --reuse-runtime`；调用方显式提供的飞书变量优先，容器内旧的空值不会覆盖新值。显式提供空字符串表示清除对应凭据。平台只展示凭据是否配置，真实权限和目标可达性以发送回执为准。

收到且归档成功的简历按任务发送到群：先上传本地校验过的原文件，再发送文件及一条任务、岗位、候选人说明。只有平台引用、尚无原文件的简历不会假报推送完成。启用通知后会补推当前任务已有的归档简历；同任务、同群、同文件摘要只推送一次。

待办通知只推送关联该任务且尚未解决的事项，接收人来自任务配置。同一待办不在每次轮询时重复提醒。账号浏览器登录问题关联共享该账号的任务；无所属任务的事项不会广播给所有管理员。飞书消息是处理提醒，实际答案和完成状态仍在平台待办中心记录；本版本不消费飞书回复或交互卡片回调。

持久化记录在数据库 `task_notification` 文档中。缺少服务端应用凭据时，已启用任务的通知明确标记为 `waiting_credentials`（等待飞书凭据），不增加发送尝试次数、不访问飞书；补齐凭据后自动继续。每个文件消息、说明消息都有稳定幂等标识和实际 `message_id`；文件已发而说明失败时不会再次发文件。明确拒绝或限流允许退避重试。网络中断导致消息响应未知时保留未知状态，不因等待超时或服务重启重复发送。关闭通知、修改接收目标、移除岗位或解决待办会阻止尚未发出的通知；已经发出的消息不自动撤回。

通知记录绑定实际发送应用 `app_id`，发送幂等标识包含该应用。更换飞书应用前，先关闭任务通知，重新核验新机器人的群权限和接收人的 Open ID，再开启。确定尚未发送的记录自动绑定新应用，并丢弃旧 `file_key`、重新上传文件；发送进行中、结果未知或已有部分消息回执的记录不得跨应用续发，会保留原应用归属并显示失败原因。已成功推送的记录继续去重，更换应用不会重推历史简历。凭据尚未配置时形成的旧等待队列在发送前完成应用绑定。

飞书客户端直接调用官方 API，候选人的简历文件不会经过 LLM 网关。来源：[消息发送](https://open.feishu.cn/document/server-docs/im-v1/message/create)、[文件上传](https://open.feishu.cn/document/server-docs/im-v1/file/create)、[应用凭据](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/authentication-management/access-token/tenant_access_token)。
