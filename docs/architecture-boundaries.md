# 执行职责与状态边界

## 分流

程序直接处理明确拒绝、稍后意愿、唯一且完整的确认答案、已授权的简历接收、信息缺口待办、资料齐备交接。模型只在有多个合理业务路径或需要理解场景时参与；未知回执、暂停和权限限制不交模型投票。确定性处理与模型提议均使用原有权限、绑定和发送校验，统一记录 actor。

## 事实

岗位事实有类型、内容、确认状态、岗位范围、来源和确认版本。旧脱敏文字仅按明确语义锚点导入；“年薪”不能作为经验年限。“未确认”或类型不对应不构成答复依据。JD 改变但原事实未重新确认时，旧事实失效，未同步的旧 FAQ 停用。管理员可在岗位回答策略中编辑事实。敏感条款仍需明确 FAQ，不从宽泛岗位文字推导。

## 动作

数据库 action_operations 与 action_leases 分别保存动作状态与对象独占占位。唯一占位与动作创建在同一事务内，保证同对象的并发写不会重复执行。状态为 prepared、claimed、executing、verified、unknown、failed，保留状态历史。占位尚未进入执行即可证明未开始，重启后可恢复为 failed；执行中断只能恢复为 unknown。

候选人发送同步已有消息占位与真实送达回执。通用写入没有专用业务回执核验器时不能仅凭点击返回宣称成功，停在 unknown。未知写入阻止同对象的新写入，即使重启或另开运行也不绕过。通用未知动作可由管理员在原系统核对后记录人工结果，明确区分人工核验和平台回执；不会自动启动任务。平台候选消息不能通过此人工接口绕过回执保护。

## 能力与传输

CapabilityRegistry 保存能力、结构化参数、只读属性和接口/浏览器/人工适配器。选路由程序根据授权和实时可用性决定，优先 API。接口写入失败不自动换浏览器重试。业务适配器可提供独立回执验证函数。没有配置真实业务 API 时仍使用浏览器，不猜测网站私有接口。模型只看到允许的能力 Schema，不能提供任意代码。站内搜索例程由程序完成验证输入框、输入、提交和读取，失败或分叉返回上层决策。

## Harness

运行时按进程内模型客户端与用途复用，原生执行进程和本机网关复用；每个决策使用新的逻辑会话，避免历史跨任务混入。系统提示词变更时创建隔离运行时，最多保留两个版本；失败时关闭受影响运行时，服务停止时清理。原生文件、shell 等工具继续禁用。执行记录保存模型会话、是否复用、调用次数与 token 用量。

## 验收

系统设置展示程序/模型决策、网关次数、复用、执行 token 与动作账本。这些是执行决策记录，不包含规划、环境测试及历史缺失数据；不是生产效果或成本收益结论。接口优先的真实收益仍需逐网站接入和测量。

## 平台资料申请

寻访 Harness 的能力新增 ask_resume（求简历）、exchange_phone（换电话）、exchange_wechat（换微信）。根据当前会话实际可用按钮开放，普通文字邀请不算平台申请卡片。优先处理候选人的问题，再由 Harness 选择资料申请；已回复且资料不齐的会话可继续推进，不必等新回复才申请。岗位“索取简历”开关控制资料申请，候选人明确拒绝或稍后、额度已满、暂停或授权变化时不执行。

同候选人同时仅保留一个待处理申请，不切换电话和微信绕过等待或拒绝。申请记录与统一动作账本先持久化再点击；已发起、回执未知、已拒绝或曾执行的同类申请均不自动再次发起。单次执行可确认唯一且与申请类型匹配的确认框，包含购买、支付等内容时不会确认。未知确认框交待办，不通过重复点击探测。

申请状态为 claimed、pending、awaiting_verification、declined、obtained 或 not_executed。pending 表示看到本方平台申请回执，不代表已取得资料；只有实际附件或候选人方向的联系方式才进入获取结果。联系方式和卡片正文保存在本机，Harness 只接收类型和状态。会话“资料申请与获取”及执行依据中可查看；未知回执待办随只读核验自动同步。

## 未知回执的分级恢复（策略 v1）

未知送达不因候选人继续交流而自动改为已送达，也不因超时而重发。真实同会话中，候选人在发送前已知历史锚点之后新增明确“可以电话联系／可以加微信”的意向，程序只开放对应的独立平台交换申请，再由 Harness 选择。执行前再次核验该上下文、授权、暂停、实际按钮和申请去重；旧消息的账本锁保持，不能借此发送新文字或重试旧消息。候选人拒绝、稍后、历史不全、会话不符或有正在发送的消息均不开启此路径。

随同账号串行调度同步回执，不因等待时长创建送达异常待办。送达未读和已读未回按所属任务的追聊策略推进，连续达到上限无回应后停止主动追聊；新的来信可以恢复沟通。无法核实的原消息保留防重发记录，不能把等待或收到回复当作该条消息送达的证明。原规划目标不变，当前 Harness 系统上下文与可用动作已更新，后续生成的规划包含相同恢复约束。任何人工解除或平台核验仍保留证据记录。

## 已读／送达证据优先

同会话、同一新增出站正文的“已读”或“送达／已送达”是直接成功证据，识别到即同步发送成功，不等待超时。标签可能位于消息节点中或仅包含该条消息的外层容器；不得借用相邻消息、会话列表或正文提到的“已读”，也不把“未读”误判为已读。回执保存实际标签与读取范围。未找到直接证据时随会话继续同步，不触发送达超时待办，也不重发原消息。

## 简历原文件与独立查看

已收到附件后，由绑定会话的浏览器点击对应附件预览／下载，监听此次页面实际返回的PDF或浏览器下载事件。原文件仅保存在本机，不发送模型。文件经类型、20MB大小和SHA-256校验后原子写入 `/data/artifacts/resumes/<case_id>/<file_id>.pdf|docx`，该目录属于 Docker 的 workspace-data 持久卷；PostgreSQL 保存候选人、来源消息、文件大小和哈希等元数据。

平台 `/api/resume-files/<id>/preview` 独立读取归档：PDF直接查看，DOCX渲染转义后的文本，原文件可下载。不依赖BOSS当前登录。接口沿用本机Host/Origin边界、候选人文件关联及完整性校验。归档失败只保留平台引用和错误，不标记为已归档；可在候选人沟通页“归档／重试已有简历”。重试只下载，不重发候选人消息；归档动作遵守当前任务暂停、管理员接管与浏览器串行约束。

## 当前寻访目标：仅取得简历（2026-11-16 用户更新）

此规则覆盖此前“简历与联系方式齐备”的历史要求。任务按收到真实附件简历的候选人数验收，电话／微信不影响完成；附件送达或同意发送与原文件归档状态继续分开展示，收到附件后仍进行本地归档。单候选人收到简历后转交，不再索要资料，旧未知发送不阻塞只读交接，但不能借交接重发消息。

新增岗位执行开关 request_contacts，默认 false，当前岗位已关闭。开启仅允许未收到简历时按原有授权与去重策略选择可选交换能力，仍不改变任务完成条件。已存联系方式、原申请和回执证据保留。任务配置、默认提示词、Harness 规划验收和持续决策、账号执行器、独立任务执行器及页面进度均采用简历人数。

## 当前运行模式：持续寻访（2026-11-16 用户纠正）

“只需简历”描述资料要求，不代表限额1份。当前任务 sourcing_mode=continuous，尽可能多取得合适候选人的简历，不设累计上限。单候选人资料齐备后交接，整个任务继续其他候选人；账号执行器与独立任务路径不因累计简历数量达到 target_resumes 自动完成。电话、微信仍可选。正常运行持续到管理员暂停或停止；每日额度、频率、防重、账号异常和人工接管边界不变。额度用完等待下一周期，不绕过平台限制。

只有显式选择 sourcing_mode=quota 的限量任务才使用 target_resumes 达标停止。页面默认展示“持续寻访”和累计数量，限量人数输入在持续模式隐藏。旧限量配置与规划保存在历史版本，当前规划与启动校验根据实际模式决定。启动账号任务按岗位 new_contacts 开关允许新寻访，同时先处理收件；初次联系仍受实际每日额度、职业范围与程序校验控制。

## 来信及时跟进与待核实回应

候选人新回复优先于新增寻访。问题有完整确认事实时直接回答；事实不足时创建管理员待办，不编造条件。转待办后，本机开放 acknowledge_pending 一次性流程回应，以第一人称确认收到并说明需要核实，不承诺待遇或时间。该回应保留 pending_question_id，不视为问题已解决；管理员补充事实／FAQ并完成重规划后再正式回答。

同一问题仅发送一次确认收到的消息，发送状态未知时禁止重复；仍受授权、暂停、候选人拒绝、每日消息上限、会话新鲜度和真实回执核验控制。已创建待办但尚未回应的问题不因旧等待缓存继续延迟，优先进入收件处理。执行依据区显示“确认收到，等待信息核实”的程序决策及实际消息回执。

## 统一候选沟通策略：薪酬与简历推进

薪酬只介绍管理员确认的结构“固定底薪＋绩效工资＋提成”，可表达整体方案合理、有竞争力，具体安排进一步详聊；不在平台对话发送金额、范围、提成比例或量化待遇。该约束进入全局沟通上下文、任务规划、岗位FAQ以及发送前校验；旧FAQ含量化数字时不能直接作为外发答案，旧已批准草稿也需通过最终发送校验。历史已发送消息保留，不重新发送修辞更新。

候选人正常回复作为继续推进信号：有问题先简短回答，再尽快索取简历，优先求简历按钮，不先多轮职业背景追问。未确认的问题先一次性确认收到并转管理员待办，随后可索取简历，不让事实补充长期阻塞资料收集。简历收集启用时不把在线资料预读放在求简历之前。明确拒绝、稍后、已收到简历和已有待处理／未知申请仍由程序阻止重复索要。联系方式依旧可选，任务仍持续寻访，不因累计简历数量结束。

## 薪酬数字追问与事实缺失的区别

询问底薪金额、薪酬数字、提成比例时，已确定的边界是“不在平台对话报价”，因此不走缺失数字→核实后报价→管理员补数字的路径。单一薪酬量化追问使用 compensation_policy 来源直接回应“进一步沟通时详聊”，再引用唯一、已启用且不含量化待遇的薪酬FAQ。已介绍过结构时不重复展开，竞争力表述仅在已确认FAQ具有相同依据时使用。涉及社保、地点等复合问题仍单独核验，不用边界话术吞掉其他问题。

平台申请的未知结果仍保留。原生求简历／换电话／换微信占位按 candidate:...:platform-request 独立保存，未知时继续阻止重复申请；普通问题答复仍执行自身授权、去重和回执核验。历史申请锁迁移为独立范围时仅记录范围调整事件，不修改成成功或失败，避免把申请待核验误用为整段对话永久锁。

## 统一低频追聊（送达与已读分开）

> 2026-11-24 起按“对话体验底线”收紧（见 `cloakup/followup.py` 顶部常量）。起因：一位候选人从未回复，首聊后 11-18 23:08、11-22 15:31（送达未读）、11-23 18:27 被连续追了三次，其中一次在深夜、一条话术与对话无关。

追聊策略由各任务的执行策略配置，但配置只能比底线更严，保存任务配置时会收敛到底线以内（`followup.limits`）：

- 从未回复过的候选人：首聊之后最多再追 1 次。
- 回复过、后来沉默的候选人：每个新回复之后最多追 2 次；新的人类回复更换 anchor、重置计数。
- 上一条只是“送达”、尚未观察到已读：不追聊，避免在对方列表里堆消息；送达后超过 `nudge_unread_hours`（默认 168 小时）仍未读，标记 exhausted，结束追聊。
- 已读未回复：至少间隔 72 小时；实际时刻在配置时长的 1.0～1.3 倍间按“候选人 + 上一条消息”稳定取值，不早于配置时长。
- 主动追聊只在上海时间 9–20 点发送，不跟随任务执行时段延到深夜；回复候选人来信不受此限。
- 话术：无回复者用一条带“暂时不考虑也没关系”的温和确认；回复后沉默者先请简历、最后一次说明不再打扰。不再轮换“联系方式可以之后再交流”这类与对话无关的句子；回答联系方式等问题走 `clarify_previous`。

时间仅用于准入，不证明候选人已读，也不自行授权发送。候选人原话、联系方式、姓名不因追聊新增披露。人工最新回复、未知回执、明确拒绝／稍后、已获得简历、暂停、每日消息上限均拦截。每次真实发送占位记入 nudge_anchor 和 nudge_number；未知发送不重发。达到上限且等待窗口内无回应，标记 exhausted，停止对该候选人的主动追聊，不删除资料、不停止其他候选人的持续寻访。

执行日报的“对话体验”一节逐个检查当天有我方消息的对话：连续未回复的主动消息数、9–20 点以外的主动消息、两条主动消息间隔不足 48 小时、追发未读消息、对方拒绝后仍主动发、对方没问过却提联系方式。

薪酬数字仍不在对话报价，可表述交换联系方式后进一步详聊，随后优先索取简历；联系方式可选，不阻塞简历收集。已有申请不重复点击，旧的薪酬回答不因修辞调整立即重发。

## 正向新回复不等待冷追聊

“好滴／好的／嗯嗯／行／可以”等新的正向确认优先进入简历邀请，不受无新回复时24／48小时追聊窗口限制。明确拒绝、没有兴趣或当前不方便仍先停止／等待。

旧求简历按钮申请等待中或回执未知时，禁止再次点击，但若此后收到真实新的正向回复且尚未收到简历，可发送一次明确的文字简历邀请。邀请以 resume_invite_for_action 关联原申请，同一申请发送中、送达未知或已送达的文字邀请均不再发第二次；既有未知出站正文仍阻止发送。新回复的待处理标识和此邀请路径绕过旧空闲缓存。此稳定事务由程序执行并记录决策、消息与回执，不扩大平台按钮重试权限，也不新增薪酬承诺。

## 简历收到后的礼貌收尾

真实收到简历后，先用当前登录账号的第一人称确认收到、礼貌感谢，说明会认真查看并及时联系，再记录交接。默认：“简历已收到，谢谢您！我会认真查看，并及时与您联系，沟通后续安排。”可在岗位沟通配置编辑，不承诺具体联系时点、面试、推荐或录用结果。

acknowledge_resume 为程序事务，仍经授权、暂停、日限额、会话新鲜度、发送占位与实际送达／已读回执核验。resume_receipt_refs 与文件哈希保存已确认范围；同份文件、别名引用、已发送或回执未知的确认不重复。已明确致谢的历史消息按附件来源时间核对，避免补发重复。仅同意接收、在线资料或按钮点击不等于收到附件；不得提前致谢宣称收件。未知旧出站消息仍保留防重保护，不伪造确认成功。

交接过但漏了确认的候选人可补齐一次收尾。新收件确认绕过空闲缓存，不套用冷追聊间隔；收到简历后停止索要简历和主动追聊，任务继续其他合适候选人的持续寻访。界面展示收件确认已发送、待发送或回执待核实，完整正文与回执留在沟通／执行依据中。

## 对话脱敏：只隐去身份与联系方式（2026-11-24 管理员确认）

此前对话理解前的脱敏遇到拿不准的片段（“我在武汉”、“X女士”、英文单词、附件文件名）会整段拒绝，候选人一直收不到回复，也没有管理员待办（候选人 168、20）。现改为：

- 隐去：画像中的已知姓名、“我叫／姓名／联系人”后的名字、“X先生／女士”称呼、电话／微信／邮箱／链接、证件与平台标识、长数字、年龄性别、附件文件名（只保留“[附件]”）。
- 保留：单位、学校、城市、英文单词，让模型能正常理解与回答。已知局限：候选人用英文名自称时可能保留。
- 不再整段拒绝；超长文字截到 1600 字。仍有旧的隐私暂缓时，暂缓期间只执行收简历致谢，并生成“对话需要隐私复核后人工接续”待办。
- Harness 决策载荷不变，仍只含意图标签、资料状态与已确认事实。
